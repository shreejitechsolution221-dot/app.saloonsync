# PERF-01 caching boundaries

VERIFIED by repository inspection: Redis and a public non-sensitive service catalog are absent. IMPLEMENTED: `TenantCache`, a store-independent catalog cache foundation with explicit 1–300 second TTL, tenant/schema namespace, hashed identity/role/permissions/branch/filter scope, strict schema validation, 64 KB serialized-value bounds, local single-flight coalescing capped at 128 pending entries, a 10-second local outage circuit and generation-based invalidation. Store errors fall back to authoritative reads; failed invalidation returns false. Load errors propagate. No authorization decisions are cached.

Unit tests simulate tenant/identity/role/branch separation, invalidation, a fill racing invalidation, corrupt JSON, TTL validation and store failure. These are not real Redis integration tests. The small Map store exists only in the test fixture; there is no in-memory production fallback. The abstraction is deliberately **not wired into live business reads**. DEFERRED: Redis client/transport, infrastructure and business-response caching. No paid resource was provisioned. No live Redis outage test is claimed.

The existing businessSchemaReady cache stores only schema availability, coalesces concurrent checks and retries negative checks after five seconds. Positive checks live up to one hour. The new `/api/v1/ready` probes database access independently and does not trust that cache. React.cache in authorization/workspace resolution deduplicates within a render request, not across users. Private responses remain no-store. No service worker persists private responses.

## Required design before enabling business caching

Authorize first on every hit. Construct keys only from verified server scope: `saloonsync:v1:tenant:<authorized tenant>:catalog:<hash of identity/role/permissions/allowed branches/normalized filters>`. Cache only a projected, explicitly classified read model; never tokens, sessions, personal profiles, payment records or authorization decisions. Bound key length, payload size, TTL and in-flight coalescing cardinality. Validate deserialized data against a schema, treat corrupt/oversized values as misses, and prevent JSON-unsupported values from entering the store.

Use bounded connection/command timeouts, no unbounded retries, circuit breaking and database fallback. Do not serve a cached availability result as booking authority; booking validation and overlap protection remain in PostgreSQL. Use a generation/version key or transactional outbox so invalidation wins races with in-flight cache fills. TTL alone is insufficient. An invalidation failure across replicas must not silently keep serving stale business results: document and test a durable recovery/invalidation strategy before wiring the cache.

Required integration acceptance on disposable Redis/PostgreSQL: two tenants with identical filter values never share entries; role/branch changes take effect on a would-be hit; every mutation invalidates relevant variants; a fill racing invalidation cannot republish stale data; Redis outage leaves writes correct; recovery cannot revive stale generations. A real adapter must enforce bounded connection/command timeouts and retries; the abstraction does not cancel transport operations. Generation metadata requires an eviction/durability policy so lost metadata cannot resurrect old cache values. Failed invalidation requires a durable outbox/version recovery strategy across instances, not merely a local circuit. Record hits/misses/errors without tenant or identity metric labels. Live integration is NOT IMPLEMENTED in PERF-01 and remains an explicit release limitation, not a simulated success.
